Can you tell me about a problem you encountered in your data engineering work that felt challenging, but you ultimately found a creative solution?

Answer:- “In my insurance project, we were ingesting data from 11–12 different admin systems into Google Cloud Storage. A challenge I faced was that the incoming files had inconsistent naming conventions and timestamps, which made it difficult to align the data correctly and sometimes caused pipeline failures.
My solution was to add a preprocessing step in the Bronze layer to standardize filenames and normalize timestamps before moving the data forward. I implemented simple transformation rules using Dataproc and SQL so that every file followed a consistent structure.
This creative fix ensured that the rest of the pipeline — Silver and Gold layers — ran smoothly, and the data landed cleanly in BigQuery for analytics. It turned a recurring issue into a reliable process.”
-------------------------------------------------------------------------------------------------------
inconsistent Timestamp- Imagine your raw file has a column with timestamps like 2026/07/27 01:45 or 27-07-2026 01:45.
to_timestamp(..., "yyyy-MM-dd HH:mm:ss") → converts whatever is inside that column into a proper timestamp format.

from pyspark.sql import SparkSession
from pyspark.sql.functions import col, to_timestamp, regexp_replace

# 1. Start Spark session (Dataproc cluster will handle the backend)
spark = SparkSession.builder.appName("BronzeLayerPreprocessing").getOrCreate()

# 2. Read raw files from GCS bucket
raw_df = spark.read.option("header", "true").csv("gs://your-bucket/raw-data/*.csv")

# 3. Normalize timestamps (convert inconsistent formats into a standard one)
clean_df = raw_df.withColumn(
    "event_time",
    to_timestamp(col("event_time"), "yyyy-MM-dd HH:mm:ss")
)

# 4. Standardize schema (rename inconsistent column names)
# Example: some files have 'Cust_ID', others have 'CustomerId'
if "Cust_ID" in clean_df.columns:
    clean_df = clean_df.withColumnRenamed("Cust_ID", "CustomerId")

# 5. Clean up string values (remove unwanted characters, trim spaces)
clean_df = clean_df.withColumn("CustomerName", regexp_replace(col("CustomerName"), "[^a-zA-Z0-9 ]", ""))
++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++
For string cleanup, I used PySpark’s regexp_replace function. It allowed me to remove special characters from text fields like CustomerName, Address, or City. I applied this consistently across all string columns that needed normalization.”

Q1: What is a Data Warehouse?
A: A Data Warehouse is a central repository designed to store large volumes of historical, structured data. It is optimized for analytical queries (OLAP) and supports decision-making by consolidating data from multiple sources. It is mainly used for reporting, dashboards, and trend analysis.

Q2: What are the key characteristics of a Data Warehouse?
A: A Data Warehouse is:
   - Integrated: Combines data from multiple heterogeneous sources.
   - Subject-Oriented: Organized around business domains (sales, customers, etc.).
   - Non-Volatile: Once data is loaded, it remains stable and is not frequently changed.
   - Time-Variant: Stores historical data with timestamps for trend analysis.
   - Structured: Primarily handles structured data for consistent reporting.

Q3: Difference between Database (DB) and Data Warehouse (DWH)?
A:
   - Database (DB): Designed for day-to-day operations (OLTP). Handles current, transactional data (insert, update, delete). Optimized for speed and consistency in small queries.
   - Data Warehouse (DWH): Designed for analytics (OLAP). Stores historical, aggregated data. Optimized for complex queries, reporting, and trend analysis.

Q4: Data Warehouse vs Spark
A:
   - Data Warehouse: Storage + query system for structured, historical data. Best for business intelligence, dashboards, and reporting.
   - Spark: A distributed data processing framework. Best for large-scale computation, ETL pipelines, real-time streaming, and advanced analytics (ML, graph processing).
   - In practice: Spark often processes raw data and loads it into a Data Warehouse for reporting and visualization.

Q1: Latest record per event_id in SQL
Table:
event_id   user   created_at
E1         U1     2026-01-01 10:00
E1         U1     2026-01-01 10:05
E2         U2     2026-01-01 10:00

Query:
SELECT event_id, user, created_at
FROM (
    SELECT event_id,
           user,
           created_at,
           ROW_NUMBER() OVER (PARTITION BY event_id ORDER BY created_at DESC) AS rn
    FROM events
) t
WHERE event_id = 'E2';

Answer:
Use ROW_NUMBER() with PARTITION BY event_id ORDER BY created_at DESC, then filter rn=1.

Q4: Data skew — what is it and how to reduce?
Answer:
Uneven distribution of data across partitions. Solutions: salting keys, repartitioning, broadcast joins, splitting heavy keys.

Q5: Lazy evaluation in Spark

Transformations are not executed immediately; execution happens only when an action is triggered.

Q6: Repartition vs Coalesce — how do they improve performance?
Answer:

- coalesce(): reduces partitions without shuffle.

Q10: Action vs Transformation (example)
Answer:
- Transformation: lazy, returns new RDD/DataFrame (map, filter).
- Action: triggers execution, returns result (count, collect).

Q11: Advantages of Coalesce and Repartition
Answer:
- coalesce(): efficient for reducing partitions without shuffle.

Q12: If a new column is added to a table, how can you implement partitioning on it?
Answer:
You cannot directly repartition an existing table on a newly added column. 
The correct approach is to create a new table or dataset partitioned by that column from the start. 
This ensures Spark/Hive can organize data efficiently according to the new partitioning strategy.
